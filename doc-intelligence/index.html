How I'd own CRE Document Intelligence

Primary wedge: NPL & special servicing — banks and lenders drowning in distressed loan files.

I'm a product leader with 15+ years building transaction systems in real estate. This page is the work — a product manager roadmap for an AI document intelligence platform, starting where lender pain is acute: non-performing loan workout packages.

You're not evaluating a prototype. You're evaluating how I think, prioritize, and ship. The interactive prototype linked below is an iteration tool I use to pressure-test workflow decisions — not the product itself.

The opportunity — NPL first

When a CRE loan goes non-performing, the special servicer receives a workout package: servicer reports, loan documents, T-12s, rent rolls, appraisals (as-is / as-stabilized), borrower correspondence, and modification proposals — often 200+ pages across a dozen formats. Asset resolution teams spend 2–4 hours per loan pulling UPB, DSCR, LTV, NOI, occupancy, and covenant status into workout models and credit memos. Portfolio volume makes manual intake unsustainable.

NPL is the wedge. Lenders and special servicers have the highest urgency, clearest ROI, and the most repeatable document sets. Win here → expand to acquisition (OM), agency lending, and broker workflows. The platform extracts collateral and loan data from unstructured files and delivers it into Excel workout templates, LOS systems, and API pipelines.

Product vision

Ingest NPL workout packages from cloud or upload, extract loan and collateral data with human-in-the-loop validation, deliver structured fields into the systems where workouts get decided.

I'd own this end-to-end: vision and requirements through engineering partnership, QA reliability, legal alignment on data rights, and go-to-market with sales and customer success. The platform isn't a single UI — it's an extraction engine plus a multi-channel delivery layer.

Product roadmap

Phased by business value and technical feasibility. Each phase has a clear wedge, exit criteria, and metrics before the next phase earns investment.

Phase 1 · 0–6 months

NPL foundation — workout package intake

Goal: Cut NPL package intake from ~3 hours to under 20 min per loan.

Ship

  • Cloud ingest: Box + SharePoint (lender-mandated) + Google Drive fallback
  • Classification: servicer report, loan file, T-12, rent roll, appraisal
  • Extract loan fields: UPB, maturity, rate, DSCR, LTV, delinquency status
  • Extract collateral: NOI, occupancy, rent roll, as-is value
  • Browser review UI — source highlighting, covenant flag review
  • Excel add-in — NPL workout template pull (UPB, DSCR, NOI, occupancy)

Requirements I'd write

  • Schema v1: loan{}, collateral{}, financials{}, rent_roll[]
  • Loan-to-collateral linking — one package, one property ID
  • Covenant breach detection — DSCR <1.0, LTV >100% auto-flag
  • Audit trail + SOC2-aligned ingest for bank compliance

Exit criteria

  • >92% accuracy on P0 NPL fields post-review
  • 5 bank / special servicer design partners active weekly
  • Workout Excel pull on >70% of completed extractions
Phase 2 · 6–12 months

Scale — portfolio NPL & agency lending

Goal: Batch portfolio ingest — 50+ NPL loans — plus expand to performing loan underwriting.

Ship

  • Watched folders — auto-ingest when brokers drop docs in Dropbox / Drive / Box
  • Box.com + Microsoft 365 (SharePoint / OneDrive) enterprise connectors
  • T-12 / operating statement extraction + expense normalization
  • Multi-document package view (OM + rent roll + T-12 linked by property)
  • Word add-in — IC memo field merge
  • Developer API v1 — REST extractions endpoint
  • Lender-specific export templates (DSCR inputs, occupancy, NOI bridge)

Partnerships

  • QA/DevOps: reliability SLAs, regression suite per doc type
  • Legal: derivative data rights framework with clients
  • Data science: model retraining loop from human corrections

Exit criteria

  • Full package processing <5 min median
  • API adoption by 3+ enterprise partners
  • NRR >110% on document intelligence SKU
Phase 3 · 12–18 months

Expand — new doc types & derivative products

Goal: Broaden TAM and build data products on extracted corpus.

Ship

  • Appraisal comp table extraction
  • Phase I ESA — RECs, findings, regulatory flags
  • Batch portfolio ingest (50+ properties)
  • Webhook/async API for enterprise pipelines
  • Derivative analytics: market rent benchmarks, expense ratios by asset class

GTM expansion

  • Environmental consulting & engineering firms
  • Law firms — lease abstraction path
  • Embedded API for LOS and data warehouse partners

Exit criteria

  • 5+ document types in production
  • Derivative data product revenue stream live
  • Platform NPS >40 among power users

Cloud integrations — meet firms where files already live

CRE teams don't store deal packages in your app. They live in Dropbox, Google Drive, Box, and SharePoint / OneDrive — often mandated by IT. Forcing a new upload portal adds friction and kills adoption. Ingest has to be a connector layer, not a drag-and-drop-only UI.

1 · Connect & pick

Phase 1

OAuth into the user's cloud account. Browse folders, select a deal package, pull files for extraction. Read-only scopes. Lowest engineering lift, immediate value.

Analysts, small teams, design partners.

2 · Watched folders

Phase 2

Admin or user designates a folder (e.g. /Deals/Inbox). New file lands → webhook or poll → auto-classify → queue for extraction. Brokers drop OMs; platform reacts.

Brokerages, lenders with high deal volume.

3 · Enterprise connector

Phase 2–3

IT-provisioned Box / M365 integration at org level. SSO, DLP policies, per-business-unit folder maps. Extracted JSON can write back to a structured output folder.

Banks, PE firms, 1,000+ seat accounts.

4 · API & email ingest

Phase 2

Partners push via API. Inbound deals@extract.company.com or shared mailbox for forwarded OMs. Covers firms that never standardize on one cloud.

LOS vendors, environmental consultants, API partners.

Requirements I'd own with engineering & legal

  • Read-only by default — ingest copies; never mutate source files without explicit opt-in.
  • Per-connector audit trail — source URI, connector type, who authorized, ingest timestamp.
  • Token lifecycle — refresh handling, revoke on offboarding, no long-lived broad scopes.
  • Data processing agreement — align with client cloud terms; derivative extraction rights separate from storage access.
  • Idempotent ingest — same file version doesn't re-extract; new version triggers delta or full re-run per policy.

How I prioritize

Impact

NPL workout intake is 3+ hours per loan × portfolio volume × bank willingness to pay. Highest urgency, clearest ROI — that's the wedge.

Feasibility

Extraction accuracy achievable with current models, schema complexity, and review burden. I'd rather ship 2 doc types at 94% than 6 at 80%.

Channel fit

Excel first — that's where underwriting lives. API second for enterprise. Browser is the trust layer, not the destination.

Strategic leverage

Each extraction improves the data corpus. Prioritize doc types that compound into derivative products and deepen platform moat.

Customer segments — NPL first, then expand

Special servicers & NPL asset resolution

Phase 1 wedge. Workout packages land daily. Servicer reports + collateral docs → structured loan file in hours, not days. Design partners here first.

Banks & CMBS lenders

1,000+ lender clients with NPL exposure. Box/SharePoint ingest, workout Excel templates, API into LOS. Highest contract value.

Acquisition analysts (PE, REIT)

Phase 2 expansion — distressed asset acquisitions reuse NPL extraction schemas. OM + rent roll on top of loan file model.

Investment brokers & API partners

Phase 2–3 — OM summarization, environmental consultants, white-label API once NPL schema is proven.

Go-to-market

  1. Design partners (Month 1–3): 3–5 special servicers / bank NPL desks. Co-develop workout Excel templates and covenant flag UX.
  2. Limited launch (Month 4–6): NPL package intake live. Case studies: hours → minutes per loan, portfolio throughput gains.
  3. Sales enablement: "NPL-native extraction, not generic OCR." Lead with servicer report + collateral — language lenders use.
  4. Customer success: Onboarding playbooks per persona, integration support for Excel/API, office hours.
  5. Expansion: Land with extraction → expand to API, batch, additional doc types per account.
