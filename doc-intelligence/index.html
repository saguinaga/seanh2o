How I'd own CRE Document Intelligence

End-to-end ownership of an AI document intelligence platform — extracting structure from appraisals, rent rolls, operating statements, offering memorandums, Phase I ESAs, and loan files, then delivering via browser, Office add-ins, and API. Built for brokers and lenders first; expandable across the full CRE transaction stack.

Phase 1 wedge I'd fund: NPL & special servicing — distressed workout packages land daily, ROI is measurable, doc sets are repeatable.

Lenders · NPL → Brokers · offering memos → Appraisal · ESA · API

I'm a product leader with 15+ years building transaction systems in real estate. This page is the work — how I'd run the product line from vision and requirements through GTM: prioritize by impact, ship extraction + delivery channels that earn adoption, expand doc types only when accuracy and pull rate justify the investment.

The opportunity

Brokers re-key offering memorandums and rent rolls into underwriting models. Lenders pull loan terms, appraisals, and operating statements into credit memos and LOS systems. Analysts on both sides lose hours on unstructured PDFs — and adoption dies if the product doesn't meet them in Excel, Word, and the systems they already use.

When a CRE loan goes non-performing, the special servicer receives a workout package: servicer reports, loan documents, T-12s, rent rolls, appraisals (as-is / as-stabilized), borrower correspondence, and modification proposals — often 200+ pages across a dozen formats. Asset resolution teams spend 2–4 hours per loan pulling UPB, DSCR, LTV, NOI, occupancy, and covenant status into workout models and credit memos. Portfolio volume makes manual intake unsustainable.

That's where I'd lean into NPL. Lenders and special servicers have the highest urgency, clearest ROI, and the most repeatable document sets for Phase 1. Win here → same extraction engine serves broker offering memorandums, agency underwriting, appraisals, and environmental reports. One platform; phased investment.

Product vision

Ingest unstructured CRE documents from cloud or upload — workout packages, offering memorandums, rent rolls, T-12s, appraisals — extract with human-in-the-loop validation, deliver structured data via browser, Office add-ins, and API.

I'd own this end-to-end: vision and requirements through engineering partnership, QA/DevOps reliability, legal alignment on derivative data rights, and GTM with sales and customer success. Not a single UI — an extraction engine plus a multi-channel delivery layer brokers and lenders will actually pull from.

Product roadmap

Phased by business value and technical feasibility. Each phase has a clear wedge, exit criteria, and metrics before the next phase earns investment.

Phase 1 · 0–6 months

Workout package intake

Goal: Cut workout package intake from ~3 hours to under 20 min per loan.

Ship

  • Cloud ingest: Box + SharePoint (lender-mandated) + Google Drive fallback
  • Classification: servicer report, loan file, T-12, rent roll, appraisal
  • Extract loan fields: UPB, maturity, rate, DSCR, LTV, delinquency status
  • Extract collateral: NOI, occupancy, rent roll, as-is value
  • Browser review UI — source highlighting, covenant flag review
  • Excel add-in — workout template pull (UPB, DSCR, NOI, occupancy)

Requirements I'd write

  • Schema v1: loan{}, collateral{}, financials{}, rent_roll[]
  • Loan-to-collateral linking — one package, one property ID
  • Covenant breach detection — DSCR <1.0, LTV >100% auto-flag
  • Audit trail + SOC2-aligned ingest for bank compliance

Exit criteria

  • >92% accuracy on P0 loan & collateral fields post-review
  • 5 bank / special servicer design partners active weekly
  • Workout Excel pull on >70% of completed extractions
Phase 2 · 6–12 months

Portfolio scale & agency lending

Goal: Batch portfolio ingest — 50+ loans — plus expand to performing loan underwriting.

Ship

  • Watched folders — auto-ingest when brokers drop docs in Dropbox / Drive / Box
  • Box.com + Microsoft 365 (SharePoint / OneDrive) enterprise connectors
  • T-12 / operating statement extraction + expense normalization
  • Multi-document package view (offering memorandum + rent roll + T-12 linked by property)
  • Word add-in — IC memo field merge
  • Developer API v1 — REST extractions endpoint
  • Lender-specific export templates (DSCR inputs, occupancy, NOI bridge)

Partnerships

  • QA/DevOps: reliability SLAs, regression suite per doc type
  • Legal: derivative data rights framework with clients
  • Data science: model retraining loop from human corrections

Exit criteria

  • Full package processing <5 min median
  • API adoption by 3+ enterprise partners
  • NRR >110% on document intelligence SKU
Phase 3 · 12–18 months

Expand — new doc types & derivative products

Goal: Broaden TAM and build data products on extracted corpus.

Ship

  • Appraisal comp table extraction
  • Phase I ESA — RECs, findings, regulatory flags
  • Batch portfolio ingest (50+ properties)
  • Webhook/async API for enterprise pipelines
  • Derivative analytics: market rent benchmarks, expense ratios by asset class

GTM expansion

  • Environmental consulting & engineering firms
  • Law firms — lease abstraction path
  • Embedded API for LOS and data warehouse partners

Exit criteria

  • 5+ document types in production
  • Derivative data product revenue stream live
  • Platform NPS >40 among power users

Cloud integrations — meet firms where files already live

CRE teams don't store deal packages in your app. They live in Dropbox, Google Drive, Box, and SharePoint / OneDrive — often mandated by IT. Forcing a new upload portal adds friction and kills adoption. Ingest has to be a connector layer, not a drag-and-drop-only UI.

1 · Connect & pick

Phase 1

OAuth into the user's cloud account. Browse folders, select a deal package, pull files for extraction. Read-only scopes. Lowest engineering lift, immediate value.

Analysts, small teams, design partners.

2 · Watched folders

Phase 2

Admin or user designates a folder (e.g. /Deals/Inbox). New file lands → webhook or poll → auto-classify → queue for extraction. Brokers drop OMs; platform reacts.

Brokerages, lenders with high deal volume.

3 · Enterprise connector

Phase 2–3

IT-provisioned Box / M365 integration at org level. SSO, DLP policies, per-business-unit folder maps. Extracted JSON can write back to a structured output folder.

Banks, PE firms, 1,000+ seat accounts.

4 · API & email ingest

Phase 2

Partners push via API. Inbound deals@extract.company.com or shared mailbox for forwarded OMs. Covers firms that never standardize on one cloud.

LOS vendors, environmental consultants, API partners.

Requirements I'd own with engineering & legal

  • Read-only by default — ingest copies; never mutate source files without explicit opt-in.
  • Per-connector audit trail — source URI, connector type, who authorized, ingest timestamp.
  • Token lifecycle — refresh handling, revoke on offboarding, no long-lived broad scopes.
  • Data processing agreement — align with client cloud terms; derivative extraction rights separate from storage access.
  • Idempotent ingest — same file version doesn't re-extract; new version triggers delta or full re-run per policy.

How I prioritize

Impact

Workout package intake is 3+ hours per loan × portfolio volume × bank willingness to pay. Highest urgency, clearest ROI — that's the wedge.

Feasibility

Extraction accuracy achievable with current models, schema complexity, and review burden. I'd rather ship 2 doc types at 94% than 6 at 80%.

Channel fit

Excel first — that's where underwriting lives. API second for enterprise. Browser is the trust layer, not the destination.

Strategic leverage

Each extraction improves the data corpus. Prioritize doc types that compound into derivative products and deepen platform moat.

Customer segments

Brokers and lenders are the core market — highest volume, clearest workflows. Phase 1 design partners: bank workout desks and special servicers (NPL). Phase 2: broker offering memorandums on the same engine.

Banks & CMBS lenders

Primary buyer. Distressed and performing loan workflows, Box/SharePoint ingest, workout Excel templates, API into LOS. Phase 1 NPL wedge — highest contract value and urgency.

Investment brokers

Scale play. Offering memorandums, rent rolls, and marketing packages at high volume. Watched-folder ingest, multi-doc package view, Word/Excel pull. Phase 2 once lender schema is proven.

Special servicers & asset resolution

Phase 1 wedge partners. Workout packages land daily. Servicer reports + collateral → structured loan file in hours. Where I'd co-develop covenant flag UX and Excel templates.

Environmental, legal & API partners

Phase 2–3 — Phase I ESAs, lease abstraction, white-label API, derivative analytics once core extraction earns trust.

Discovery & adoption

I wouldn't assume I know what brokers and lenders need — especially for a third-party product where adoption has to be earned, not mandated. Before scaling doc types or channels, I'd embed with users: shadow package intake, sit with analysts during Excel/LOS handoffs, and map which extracted fields actually change a decision vs. which ones look important in a demo.

Design partners aren't a checkbox. They're how I'd validate delivery (browser vs. add-in vs. API), correction burden, and whether cloud ingest beats upload for each persona. Weekly active extractors and channel pull rate matter more than feature count — if nobody pulls to Excel, extraction is a science project.

Go-to-market

  1. Design partners: 3–5 bank workout desks and special servicers — NPL package intake, covenant flags, lender Excel templates.
  2. Limited launch: Lender workflow live. Case studies: hours → minutes per loan. Broker offering-memorandum pilot with 2–3 firms.
  3. Sales enablement: Lender track: "NPL-native extraction, not generic OCR." Broker track: "Offering memorandum + rent roll in your model, not in your inbox."
  4. Customer success: Persona playbooks — lender LOS/Excel integration, broker watched-folder setup, API onboarding.
  5. Expansion: Land with lender extraction → broker offering memorandums → API, batch, appraisal & ESA doc types per account.
